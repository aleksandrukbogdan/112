# Тренажёр оператора Системы-112

Симулятор приёма экстренного вызова с ИИ-заявителем и автоматической оценкой.
Обучаемый принимает звонок, ведёт опрос, заполняет карточку и направляет её в ДДС —
система оценивает и содержание опроса, и манеру его ведения.

Норматив опроса — **75 секунд** (ПП РФ № 1931, п. 9 подп. р). Состав карточки — оттуда же.

---

## Как это работает

**Сценарий — структура данных, а не промпт.** У происшествия есть список фактов,
у каждого — условие раскрытия. Заявитель называет улицу только если оператор спросил
адрес, квартиру — только если уточнил отдельно, про ребёнка в комнате — только если
спросил про пострадавших. Нераскрытые факты не попадают ни в промпт модели, ни в ответ,
поэтому выдумать их невозможно.

**ИИ извлекает признаки, правила ставят баллы.** Модель классифицирует реплику оператора
и отыгрывает роль заявителя. Оценку считает детерминированный движок по чек-листу —
в `scoring.py` нет ни одного обращения к модели.

**Всё пишется в ленту событий.** Метрики не хранятся, а выводятся из `session_event`.
Поэтому смена порогов пересчитывает всю историю, не трогая исходные данные, а разбор
одного вызова и сводка по потоку берутся из одного источника и не могут разойтись.

## Что уже готово

| | |
|---|---|
| Бэкенд | FastAPI: сессии, движок сценария, классификатор интентов, скоринг, WebSocket |
| Фронт | Next.js: АРМ обучаемого, АРМ преподавателя, панель аналитики |
| БД | Postgres, событийная схема, представления для аналитики |
| Сценарий | «Пожар в квартире» — 8 фактов, 9 пунктов чек-листа, 6 инъекций |
| Речь | ASR (GigaAM) и TTS (Silero) — отдельным профилем, включаются по готовности |
| Голос в браузере | Запись с микрофона, автонарезка реплик по паузе, измерение пауз |
| Голосовой банк | Предсинтез реплик сценария в кэш — реплики играют мгновенно |
| Протокол | Выгрузка разбора в PDF с полем для подписей |
| Проверки | 5 скриптов: логика, интенты, сквозной вызов, задержка, предсинтез |

**Текстовый режим работает без речевых моделей и без LLM.** Это не заглушка: на нём
отлаживается вся логика сценария и оценки, и он же остаётся аварийным режимом на демо.

# Пошаговая установка

Каждый шаг заканчивается проверкой. Не переходите к следующему, пока не сошлось.

## Требования

- Docker и Docker Compose
- Python 3.9+ на хосте (для скриптов проверки)

```bash
docker --version && docker compose version && python3 --version
```

### Порты

По умолчанию используется блок **21120–21125**. Он выбран намеренно: ниже
эфемерного диапазона Linux (тот начинается с 32768) и не пересекается с
привычными 3000, 5432, 6379 и 8080, которые на рабочем сервере почти всегда
уже кем-то заняты.

| Порт | Сервис |
|---|---|
| 21120 | веб-интерфейс |
| 21121 | API |
| 21122 | Postgres |
| 21123 | Redis |
| 21124 | ASR (профиль speech) |
| 21125 | TTS (профиль speech) |

```bash
make ports
```

Если что-то занято, скрипт покажет, кто держит порт, и сразу предложит
свободные значения для `.env`. Всё настраивается — ничего не прибито гвоздями.

**Одна ловушка.** Браузер обращается к API напрямую, поэтому при смене
`API_PORT` обязательно меняется и `NEXT_PUBLIC_API_URL`:

```
API_PORT=21221
NEXT_PUBLIC_API_URL=http://localhost:21221
```

`make up` сам вызывает проверку и не станет разворачиваться на занятых портах.

## Шаг 1. Развернуть текстовый режим

```bash
cp .env.example .env
nano .env            # обязательно задайте PG_PASSWORD
make ports           # убедиться, что порты свободны
make up
```

`make up` собирает образы, поднимает Postgres, API и фронт, ждёт готовности API
и печатает состояние.

### Проверка

```bash
make health
```

Должно быть примерно так:

```json
{
  "ok": true,
  "checks": {
    "api": true,
    "db": true,
    "llm": { "ok": false, ... },
    "asr": { "ok": null, "note": "выключен" },
    "tts": { "ok": null, "note": "выключен" }
  }
}
```

Ключевое — `"db": true`. Речевые модели и LLM на этом шаге не нужны.

**Если API не отвечает:**

```bash
docker compose logs api --tail=50
```

Частые причины: не задан `PG_PASSWORD`, занят порт 8080, БД ещё стартует
(API ждёт её до 60 секунд).

## Шаг 2. Проверить логику без сети

Эти тесты не требуют ни Docker, ни БД — только Python.

```bash
make test
```

Выполняется два набора:

**`test_intents.py`** — 21 формулировка вопросов оператора против правил классификатора.
Ловит ложные сработки. Например, при разработке он поймал, что «кто-то есть в квартире?»
распознавалось как вопрос об адресе из-за слова «квартир», а «на балконе есть баллоны?» —
как вопрос об эвакуации из-за слова «балкон». Оба правила пришлось уточнить.

**`test_logic.py`** — четыре сценария:
- хороший прогон должен быть зачтён,
- прогон без адреса, с грубостью и не той службой — не зачтён, с тремя стоп-факторами,
- факт `f_child` сам раскрывается через 90 секунд, если не спросили,
- без нужного вопроса факты не раскрываются вообще.

### Проверка

В конце должно быть `21 из 21 прошли` и `ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ`.

Прогоняйте `make test` после **каждой** правки `intent_rules` в сценарии.

## Шаг 3. Сквозной прогон через API

```bash
make smoke
```

Скрипт проводит настоящий вызов от начала до конца и проверяет восемь шагов:
доступность сервисов, загрузку сценариев, начало вызова, раскрытие сведений по вопросам,
**защиту от выдумывания фактов**, карточку с верным и ошибочным значением, маршрутизацию
и оценку, ленту событий и попадание вызова в аналитику.

### Проверка

`ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ. Цепочка работает целиком.`

Отдельно обратите внимание на шаг 5: он подтверждает, что заявитель не назвал адрес,
пока его не спросили. Это ядро замысла, и оно проверяется автоматически.

## Шаг 4. Открыть интерфейсы

Откройте <http://localhost:21120>

Три раздела:

**`/trainee` — рабочее место обучаемого.** Тёмный «пульт»: софтфон, бегущая полоса
75 секунд, лента диалога, карточка происшествия по составу ПП 1931, выбор служб.
Выберите сценарий, нажмите «Принять вызов» и ведите опрос текстом.

Попробуйте намеренно спросить не то — заявитель переспросит и ничего не сообщит.
Потом спросите адрес — и он назовёт улицу, но не квартиру.

**`/instructor` — рабочее место преподавателя.** Светлый «протокол». Вставьте
идентификатор сессии (виден в логах API: `docker compose logs api | grep session`)
и подключитесь. Появятся live-метрики, кнопки инъекций и ручной зачёт вопроса.

**`/analytics` — панель аналитики.** Пока проведённых вызовов меньше трёх, показывает
демонстрационные данные — иначе панель пустая и разрабатывать её невозможно. Плашка
в шапке честно сообщает, что за данные на экране.

### Проверка

На главной странице все четыре индикатора состояния отрисовались, три раздела
открываются, вызов в `/trainee` начинается и заявитель отвечает.

## Шаг 4б. Доступ с другого компьютера

По умолчанию всё привязано к `127.0.0.1` — открыть можно только с самого сервера.
Есть два способа получить доступ с ноутбука, и они не равноценны.

### Способ 1: SSH-туннель (рекомендуется)

```bash
make tunnel
```

Команда напечатает готовую строку — выполните её **на своём компьютере**:

```bash
ssh -N -L 21120:localhost:21120 -L 21121:localhost:21121 логин@адрес-сервера
```

Пока команда выполняется, открывайте <http://localhost:21120>.

Почему именно так: **микрофон работает только здесь**. Браузеры дают доступ
к микрофону лишь в защищённом контексте — это `https` либо `localhost`.
Обычный `http://192.168.x.x` таковым не считается, и голосовой ввод в нём
просто не включится, без внятного сообщения об ошибке.

Дополнительно: ничего не нужно менять в `.env`, и сервер не открывается в сеть.

### Способ 2: открыть порты в сеть

Если микрофон не нужен — например, показываете аналитику коллегам:

```bash
# .env
BIND_HOST=0.0.0.0
NEXT_PUBLIC_API_URL=http://192.168.1.50:21121     # ← реальный IP сервера
```

```bash
docker compose up -d
```

Адрес узнать: `hostname -I | awk '{print $1}'`

Две оговорки. `NEXT_PUBLIC_API_URL` — это адрес, который использует **браузер**,
поэтому `localhost` там не подойдёт: для чужого компьютера localhost это он сам.
И контейнер `web` нужно именно пересоздать, а не перезапустить — переменная
читается при старте процесса Next.

Микрофон в этом режиме работать не будет. Если он всё же нужен без туннеля,
остаётся третий путь — поставить впереди обратный прокси с сертификатом
(Caddy получает Let's Encrypt автоматически) и ходить по `https`.

Откройте <http://localhost:21120/analytics>. Плашка должна смениться на

Проверьте фильтры: выберите группу, сценарий, поставьте «только вне норматива».
Числа наверху должны пересчитаться.

## Шаг 6. Подключить языковую модель

До этого шага классификатор работает только на правилах. LLM нужна, чтобы понимать
формулировки, которых нет в ключевых словах, и чтобы заявитель отвечал разнообразнее.

LLM разворачивается **отдельно** и в этот compose не входит.

В `.env`:

```bash
LLM_BASE_URL=http://host.docker.internal:1212/v1
LLM_MODEL=Qwen3-VL      # это --served-model-name, а НЕ путь к весам
LLM_ENABLED=true
```

```bash
docker compose up -d api
make health
```

### Проверка

В `/health` должно быть `"llm": {"ok": true, "models": [...]}`, и в списке моделей
присутствовать значение из `LLM_MODEL`.

Затем в `/trainee` задайте вопрос формулировкой, которой нет в правилах —
например, «Скажите, по какому адресу выезжать бригаде». Правила её не поймают,
а модель должна распознать `asked_address`.

**Две тонкости под vLLM:**

1. Имя модели — это `--served-model-name`. Если передать путь к весам, будет 404.
2. При `--enable-prefix-caching` статичная часть промпта должна идти первой,
   а меняющаяся последней. В `llm.py` так и сделано: system-сообщение неизменно,
   реплика оператора — в user. Тогда KV-кэш переиспользуется между ходами диалога
   и второй-третий ход считается заметно быстрее.

## Шаг 7. Подключить речь

Самый долгий шаг: веса GigaAM качаются при первом старте контейнера.

Если в `/health` видно `"asr": {"ok": false, "error": "Name or service not known"}` —
это не поломка. Так выглядит невключённый профиль: контейнеров `asr` и `tts`
попросту нет, и API не может их разрешить по имени. Всё остальное при этом
работает, потому что текстовый режим речевых моделей не требует.

```bash
python3 scripts/preload_models.py      # Silero TTS и VAD, ~60 МБ
```

В `.env` включите `ASR_ENABLED=true` и `TTS_ENABLED=true`, затем:

```bash
make up-speech
docker compose logs -f asr             # ждите строку "ASR ... loaded"
```

Что происходит при первом запуске: собирается образ с PyTorch и CUDA
(несколько минут), затем скачиваются веса GigaAM — модель распознавания
и модель эмоций. Обе кладутся в `models/`, который смонтирован с хоста,
поэтому повторные старты уже мгновенные.

Речевые модели идут на GPU, заданную в `SPEECH_GPU` (по умолчанию 1).
Нулевую занимать не нужно, если на ней стоит языковая модель.

### Проверка

```bash
make health                            # asr и tts должны стать ok: true
python3 scripts/smoke_latency.py -n 5
```

Скрипт гоняет полную цепочку **голос оператора → ответ заявителя в аудио**
и раскладывает задержку по слагаемым: ASR, классификация, генерация реплики, синтез.

**Бюджет — 1000 мс до первого звука.** Это критерий приёмки, а не пожелание.
Если не укладываетесь, режьте живые вычисления, а не функциональность:

1. Предсинтез: реплики сценария синтезировать заранее, играть из кэша.
2. Слить классификацию интента и генерацию реплики в один вызов модели.
3. Стриминг TTS: отдавать первый чанк, не дожидаясь конца фразы.
4. Филлеры: вдох или всхлип из банка играет сразу, пока считается ответ.

**После первого успешного старта заархивируйте каталог `models/`.** На площадке
хакатона интернет обычно плохой, а веса качаются долго.

```bash
tar czf models-backup.tar.gz models/
```

## Шаг 8. Голосовой ввод и предсинтез

После того как речевые модели поднялись, включается всё остальное.

### Голос в браузере

Откройте `/trainee`, начните вызов и нажмите **«Перейти на голос»**. Браузер
запросит доступ к микрофону.

Два режима записи:

- **нарезка по паузе** — реплика отправляется сама, когда вы замолчали примерно
  на секунду. Так это работает в настоящем разговоре;
- **удержание кнопки** — для шумных помещений и для демо, где случайный звук
  не должен улететь в распознавание.

Индикатор уровня показывает, слышит ли вас система. Под лентой видно, что именно
она распознала — это важно: если оператор сказал одно, а ASR услышал другое,
разбираться нужно сразу.

Клиент замеряет **паузу перед репликой** и передаёт её вместе с аудио. Без этого
ось «манера» всегда была бы идеальной: восстановить длину паузы постфактум по
записи уже нельзя.

Паузы засчитываются только когда очередь оператора. Если в этот момент говорил
заявитель или преподаватель добавлял помеху, это не растерянность оператора.

### Предсинтез голосового банка

```bash
python3 scripts/prewarm_voicebank.py --check    # посмотреть, что будет синтезировано
make prewarm                                     # синтезировать
```

Скрипт собирает **все** реплики заявителя из сценариев — первую фразу, озвучку
каждого факта, заготовки на все уровни стресса, реплику переспроса — и прогоняет
их через TTS с теми же параметрами, что использует боевой код. Файлы оседают
в `voicebank/`.

Смысл в бюджете задержки. Живая цепочка распознавание → модель → синтез в секунду
не укладывается. Но реплики заявителя известны заранее, поэтому во время вызова
они играют из кэша за считанные миллисекунды, а живой синтез остаётся только для
редких свободных ответов.

Побочная выгода: панические реплики можно переслушать и переозвучить офлайн,
а не надеяться на удачную генерацию в реальном времени.

### Проверка

```bash
python3 scripts/smoke_latency.py -n 5
```

После предсинтеза медиана должна заметно упасть. Если всё ещё не укладывается
в 1000 мс — смотрите разбивку по слагаемым: она покажет, кто именно тормозит.

## Шаг 9. Протокол в PDF

```bash
make pdf        # скачает протокол последнего завершённого вызова
```

Или прямо из интерфейса: кнопка **«Скачать протокол»** на экране разбора
в `/trainee` и в микро-разборе аналитики.

Протокол содержит шапку с обучаемым и попыткой, оценку по трём осям с заключением,
полосу 75 секунд в бумажном виде, таблицу соблюдения временных параметров, полноту
опроса по чек-листу с таймкодами и баллами, показатели устойчивости, полную ленту
вызова и **поля для подписей преподавателя и обучаемого**.

Это не «экспорт для галочки». Нормативные требования предполагают итоговую
аттестацию с выводом результатов контроля в баллах, а комиссия работает с бумагой.

### Проверка

```bash
make smoke      # шаг 9 проверяет генерацию PDF автоматически
```

Откройте `protokol.pdf`. Кириллица должна читаться. Если вместо букв квадраты —
в образе нет шрифта: `docker compose build api` пересоберёт его с `fonts-dejavu-core`.

# Как добавить свой сценарий

Положите JSON в `content/scenarios/` и перезапустите API — он заливает сценарии
в базу при старте. Кода трогать не нужно.

```bash
cp content/scenarios/fire_apartment_01.json content/scenarios/dtp_01.json
nano content/scenarios/dtp_01.json
docker compose restart api
make test          # обязательно: правила интентов могли начать пересекаться
```

Обязательные части файла:

| Ключ | Что задаёт |
|---|---|
| `facts[]` | что известно заявителю и при каком вопросе он это скажет |
| `reveal_if` | список интентов, любой из которых раскрывает факт |
| `spontaneous_after_sec` | через сколько заявитель выкрикнет сам, если не спросили |
| `checklist[]` | пункты оценки, баллы и штраф за пропуск |
| `forbidden[]` | запрещённые формулировки и их цена |
| `intent_rules` | ключевые слова классификатора |
| `timing` | цели по времени, декомпозиция норматива 75 секунд |

# Что делать, если сломалось

| Симптом | Причина и что делать |
|---|---|
| `make up` падает на `PG_PASSWORD` | не создан `.env` — `cp .env.example .env` |
| `make up` останавливается на проверке портов | так и задумано. Впишите в `.env` предложенные значения и повторите |
| Фронт открывается, но данных нет | `NEXT_PUBLIC_API_URL` не совпадает с `API_PORT` |
| «Нечем проверить порты» | нет ни `python3`, ни `ss`, ни `lsof` — поставьте любой |
| API не поднимается | `docker compose logs api --tail=50`; чаще всего БД ещё стартует |
| Схема БД не накатилась | скрипты из `db/` выполняются только при **первом** создании тома. `make reset` пересоздаст |
| Фронт долго стартует | первый `npm install` в контейнере занимает 1–2 минуты, следите: `docker compose logs -f web` |
| `409 Сессия не активна` | состояние вызова живёт в памяти API; после перезапуска контейнера начните вызов заново |
| Классификатор не понимает вопрос | добавьте формулировку в `intent_rules` и в `scripts/test_intents.py`, прогоните `make test` |
| Заявитель называет то, чего не спрашивали | проверьте `reveal_if` факта и не сработало ли `spontaneous_after_sec` |
| LLM возвращает 404 | в `LLM_MODEL` должно быть `--served-model-name`, а не путь к весам |
| Аналитика пустая | `make seed` |
| Аналитика показывает демо-данные | нужно минимум 3 завершённых вызова |
| `asr`/`tts`: `Name or service not known` | профиль speech не поднят — это нормально до шага 7 |
| Фронт с другого ПК открывается, но пустой | `NEXT_PUBLIC_API_URL` указывает на `localhost` вместо IP сервера |
| Поменяли `NEXT_PUBLIC_API_URL`, ничего не изменилось | нужно пересоздать контейнер: `docker compose up -d web` |
| Микрофон не включается с другого ПК | так и будет по `http`. Используйте `make tunnel` |
| `docker logs api` — нет такого контейнера | имена с префиксом: `docker logs t112-api` или `docker compose logs api` |
| Реплика не отправляется в режиме паузы | говорите громче либо переключитесь на удержание кнопки |
| `422 Речь не распознана` | норма при кашле или шуме, ход просто пропускается |
| В PDF вместо букв квадраты | нет шрифта с кириллицей: `docker compose build api` |
| `make prewarm` пишет «TTS выключен» | `TTS_ENABLED=true` в `.env` и `make up-speech` |

# Ближайшие шаги

Порядок по убыванию отдачи.

1. **Ещё два сценария** — ДТП и запах газа. Разные ДДС показывают маршрутизацию.
   Файлы, не код.
2. **Расширить `test_intents.py`** до 100 формулировок. Классификатор — самое
   хрупкое место, и набор фраз это единственная защита.
3. **Записать банк эмоций** — крики, всхлипы, вдохи. Полчаса командой, а качество
   паники вырастает сильнее, чем от любой модели.
4. **Библиотека трудных заявителей** — ребёнок, пожилой слабослышащий, нетрезвый,
   агрессор, молчащий вызов, иностранец. Последние два прямо в нормативе.
5. **Режим аттестации** — фиксированный набор сценариев и сводный протокол.
6. **Адаптивный подбор** — тепловая карта в аналитике уже показывает слабые зоны,
   осталось связать её с выбором следующего сценария.

**Чего не делать:** не выдумывать значения классификаторов происшествий. Их структура
задана ПП 1931, а содержание должен дать заказчик. Придумаете своё — придётся переделывать.
