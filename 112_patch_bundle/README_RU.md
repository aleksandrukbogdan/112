# Патчи тренажёра 112 / ДДС

База: исходники, извлечённые из `112 (10).txt` в рабочей папке беседы. Это проверяемый набор изменений, а не подтверждённый production-релиз. Ваш работающий сервер и ветка коллеги здесь не изменялись.

## Что внутри

| Пакет | Изменения | Зачем |
|---|---|---|
| 01 | Компоненты адреса, критические условия зачёта, скрытие эталонов, поправки прогноза и BKT | Не засчитывать неверный адрес/маршрут и не объявлять непроверенный навык освоенным |
| 02 | Миграции, снимки сценария/классификатора/правил, журнал действий, транзакции, сохранённый ответ завершения | Воспроизводимый разбор; повторное завершение не начисляет навыки второй раз |
| 03 | Разбор с событиями, отдельные программы 112/ДДС, пересмотр критериев, аналитика, персональный план | Показать причины результата и следующий учебный шаг |
| 04 | Отключаемая прогнозная ML-модель, экспорт/обучение/проверка, приёмочные тесты и исправления совместимости | Проверять прогноз на независимых данных, а интеграцию — на реальном приложении |

`all.patch` объединяет всю серию. **Применять весь комплект.** Отдельные `patches/*.patch` предназначены для просмотра истории и последовательного переноса; частично применённая серия не проходила итоговую приёмку. Не применять одновременно `all.patch` и отдельные патчи.

Порог балла остаётся 70. В режиме 112 обязательны адрес, тип, службы и полнота; в ДДС — подтверждение, проверка карточки, передача, обоснованность статусов и завершение. Тайминг дополнительно влияет на балл. Это реализованная учебная рубрика: преподаватель должен утвердить именно такой набор обязательных условий, а не считать его новым официальным нормативом.

## Голос и работа коллеги

Не меняются `api/caller.py`, функции API ASR/TTS, обработчики микрофона и воспроизведения. Контрольные хеши этих границ включены в тесты. Контейнеры `voice`, `asr`, `llm`, их образы и модели не пересобираются.

Меняются общие `api/main.py`, `api/dds.py`, `web/app.js`, `web/dds.js`. Если коллега правит их, возможен текстовый конфликт. Утилита сначала вызывает `git apply --check`; при конфликте останавливается. Даже чистое применение требует запуска голосового сценария: неизменность функций не доказывает отсутствие косвенного влияния нагрузки/задержек. Если хеш голоса отличается из-за согласованных изменений коллеги, сравнить изменения вручную; не перезаписывать эталон теста только ради зелёного результата.

## Применение

Сначала отдельная ветка/копия работающего проекта. Команды из распакованного архива:

```bash
python apply_patches.py /полный/путь/к/проекту
python apply_patches.py /полный/путь/к/проекту --apply
```

Первый вызов ничего не меняет. Второй создаёт резервную копию затронутых исходников во временной папке и применяет патч. Путь копии выводится; перенесите её в надёжное место, если нужна длительная история. Настройки окружения, ключи, веса моделей и содержимое БД утилита не копирует и не изменяет. Для интеграции с коллегой предпочтительнее Git-ветка и обычное ревью diff.

В рабочем окружении до выкладки: завершить активные занятия, сделать резервную копию через «Администрирование → резервная копия» и проверить восстановление на стенде. Затем пересобрать и перезапустить **только приложение**:

```bash
docker compose build app
docker compose up -d --no-deps app
```

Новые таблицы создаются автоматически при старте. Старые строки не удаляются. Никаких `down -v`, очисток `state` или принудительного сброса Git не требуется.

В экспорте отсутствует `requirements.txt`, хотя исходный Dockerfile его использует. Сохраните реальный файл зависимостей из вашего проекта. Патчи не подменяют его выдуманным lock-файлом. Если этого файла нет и в проекте, сначала восстановите его из рабочей сборки: пересборку нельзя считать воспроизводимой без него.

## Совместимость и ограничения

- Целевая версия Python — **3.12**, как в исходном Dockerfile. Новых обязательных Python-пакетов и весов моделей нет. FastAPI, Pydantic, HTTPX, ReportLab, OpenPyXL, python-multipart и psycopg остаются из вашего рабочего окружения. Для проверок JS нужен Node.js на машине тестировщика; приложению в браузере Node не требуется.
- **Ровно один worker API и одна реплика приложения.** Активные занятия остаются в `LIVE`. HTTP-запросы `/api/*`, кроме ASR/TTS, сериализуются; это закрывает гонки текущей архитектуры, но долгий ответ LLM задержит другие запросы приложения. Перед показом группе измерить задержки. Масштабирование требует отдельного изменения архитектуры хранения активных сессий.
- Миграция добавляет `schema_migrations`, `content_versions`, `session_events`, `completion_receipts`, `evidence_reviews`. Завершение, BKT, результаты прогнозов и квитанция завершения пишутся одной транзакцией. Повтор завершения возвращает первый ответ, даже если преподаватель позже пересмотрел критерии; актуальный пересмотр виден в разборе/аналитике.
- Старые завершённые попытки не пересчитываются новой рубрикой. Новая персональная аналитика показывает число исключённых архивных попыток. Старые BKT-строки сохранены; новые ключи `ops112:*` и `dds:*` начинают отдельную историю, без переноса сомнительных старых наблюдений.
- Для незавершённой попытки без прежних снимков при первом запуске создаётся снимок текущей конфигурации с пометкой `upgrade_not_original`. Он не выдаётся за историческую версию. Поэтому лучше завершить занятия до обновления.
- Ручной балл не отменяет критические ошибки. Отдельный пересмотр критериев доступен преподавателю, требует причины, сохраняет первоначальную оценку и пересчитывает BKT соответствующей программы по актуальным критериям.
- Адреса проверяются консервативно по компонентам. Дом/корпус/строение не взаимозаменяемы; полного геокодера и нормализации всех сокращений нет. Равнозначный необычный адрес может потребовать пересмотра преподавателем. Речь/грамматика и передача смысла в ДДС остаются проверками по правилам; это не полноценная семантическая экспертиза.
- Текущий групповой экран и формы 1/112 относятся к режиму 112. Подробная персональная аналитика переключается между 112 и ДДС. Для старых отчётов сохранена совместимость; новые доверительные интервалы не отменяют зависимость повторных попыток одного человека.

## Проверка

Порядок и конкретные ожидаемые результаты — в `TESTING_RU.md`. Фактически выполненные проверки — в `VALIDATION_RU.md` и логах.

```bash
cd /полный/путь/к/проекту
python scripts/verify_patch.py
python scripts/verify_patch.py --integration
```

Первый запуск: 24 Python-теста, синтаксис, 5 JS-сценариев с упрощённым DOM и границы голосового кода. Второй дополнительно требует настоящий FastAPI TestClient. Пропуск обязательной интеграции возвращает ненулевой код; надпись `unittest OK (skipped=...)` сама по себе не является приёмкой.

## Дополнительный ML

Модель `logistic-l2+platt-v1`, формат признаков `call-deadline-v1`. Это прозрачный CPU-baseline на стандартной библиотеке, не новая голосовая/языковая модель. BKT остаётся с явно обозначенными необученными параметрами; обученный BKT здесь не обещается.

Прогнозная цель — **будет ли карточка отправлена до временного порога**, а не правильность карточки или допуск к работе. Пока ML выключен, сохраняются числовые признаки на момент прогноза: доля времени/заполненных полей, число реплик/изменений, сложность. Эталон, финальный балл и будущие события в признаки не входят.

После накопления реальных завершённых попыток, в окружении приложения:

```bash
python -m scripts.ml_export /безопасная/папка/dataset.json
python -m scripts.ml_train /безопасная/папка/dataset.json /безопасная/папка/candidate.json
```

Экспорт содержит псевдонимы обучающихся и время, поэтому доступ к нему всё равно ограничивать. Не смешивать несколько экспортов: каждый создаёт новую соль псевдонимизации.

Минимум 200 попыток. Хронологическое разбиение 60/20/20; для калибровки и теста берутся только новые обучающиеся, не присутствующие в предыдущих частях. В каждой части нужны минимум 30 попыток, 10 обучающихся и оба исхода. При недостатке данных обучение останавливается. Сравнение — с постоянной вероятностью, рассчитанной только на train; метрики Brier/log loss/accuracy и групповой bootstrap разницы Brier. Повторные эксперименты по одному test-набору требуют нового контрольного набора.

Обычное обучение сохраняет `approved=false`. После изучения отчёта допускается повторить команду с `--approve`; активируемый артефакт получится только при прохождении статистического порога. Это необходимая проверка кандидата, не гарантия качества на будущем потоке. Никакой обученной на реальных данных модели в архиве нет.

Для Docker разместить проверенный `call-model.json` в `state/app/ml/` и добавить в `environment` **только сервиса app**:

```yaml
ML_FORECAST_ENABLED: "true"
ML_FORECAST_MODEL: /app/state/ml/call-model.json
```

Одной записи в `.env` недостаточно, если compose не передаёт её в контейнер. По умолчанию флаг `false`. При отсутствующем/неподтверждённом/несовместимом JSON приложение возвращается к подписанной эвристике. После дедлайна прогноз равен нулю независимо от ML. Для отключения поставить `false` и перезапустить только `app`.

## Откат

До запуска новой версии можно отменить только исходники:

```bash
python apply_patches.py /полный/путь/к/проекту --reverse
python apply_patches.py /полный/путь/к/проекту --reverse --apply
```

Утилита не откатывает БД и не удаляет новые таблицы. Если после выкладки появились новые попытки, восстановление старой резервной копии потеряет их; сначала сохранить текущую БД. Возврат старого кода также возвращает старые ошибки оценивания. Автоматического разрушительного downgrade в комплекте нет.
