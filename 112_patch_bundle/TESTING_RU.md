# Приёмка: сначала автоматически, затем вручную

## 1. Автоматически на машине разработки

В корне **уже пропатченного** проекта:

```bash
python scripts/verify_patch.py
python scripts/verify_patch.py --integration
```

Ожидание: первый прогон — 24 Python-теста, 5 JS-сценариев, синтаксис и хеши голоса. Второй — дополнительно 8 API-тестов. Требуются реальные зависимости приложения, а не заглушки FastAPI. Любое `ERROR`, `FAIL`, `NOT ACCEPTED`, ненулевой exit code или пропуск API-проверок означает, что этот уровень проверки не пройден.

Проверки создают временную SQLite-базу и тестовых пользователей. Рабочую БД не используют. Проверяется: закрытый разбор до завершения, отсутствие эталонов, чужие попытки, неверный адрес, конкурентное завершение, ДДС без передачи, роли пересмотра, неизменность исходной оценки, неподходящее назначение, снимки правил, PDF и выдача JS.

Важно: отправка одинакового финального запроса несколько раз должна дать **полностью одинаковый JSON**, одну квитанцию завершения и одно событие `session_completed`. Увеличение `bkt.n` — один раз за наблюдаемый навык, а не за каждый запрос.

Если рабочее окружение только в Docker, из корня проекта после сборки `app`:

```bash
docker compose run --rm --no-deps -v "$PWD:/work:ro" -w /work app python scripts/verify_patch.py --integration --skip-js
```

Скрипт принудительно создаёт временную SQLite-базу, несмотря на production `DATABASE_URL` в compose. Подключение к LLM для тестов выключено. Отдельно на машине с Node:

```bash
node --check web/app.js
node --check web/dds.js
node --check web/insights.js
node tests/frontend_smoke.cjs
```

## 2. PostgreSQL отдельно

SQLite не доказывает корректность PostgreSQL. Использовать отдельную тестовую БД PostgreSQL 16 и установленный psycopg из рабочего окружения. Передать её DSN через переменную среды `TEST_DATABASE_URL` (не публиковать значение в чате/логах) и включить `RUN_POSTGRES_TESTS=1`:

```bash
python scripts/verify_patch.py --postgres
```

Тест создаёт случайную отдельную схему `t112_patch_test_*`, проверяет транзакцию/rollback, миграцию и возврат `id`, затем удаляет **только свою схему**. Нужен пользователь с правом создания схемы в тестовой БД. Не использовать production superuser. Если тест аварийно оборван, может остаться его пустая/тестовая схема — удалить её вручную после проверки имени.

Это небольшой SQL smoke, а не полный нагрузочный API-прогон на PostgreSQL. На стенде с рабочим compose дополнительно выполнить ручные сценарии ниже и восстановление резервной копии.

## 3. Ручная функциональная приёмка

Использовать отдельные браузерные профили обучающегося и преподавателя. Обновить страницу с очисткой кеша. DevTools → Network и Console оставить открытыми. Внести результат каждого пункта: пройден/не пройден, session_id, скриншот, ошибка консоли при наличии.

| Проверка | Действия | Ожидаемый результат |
|---|---|---|
| Адресные роли | Для билета с «дом 1, корпус 12» ввести «дом 12, корпус 1» | Критическая ошибка адреса, итог «не зачтено», даже при балле выше 70 |
| Нормальный адрес | Ввести адрес билета полностью; затем проверить стандартные `г.`, `ул.`, `д.`, `корп.` | Полный вариант засчитан; неоднозначное сокращение не должно давать ложный зачёт |
| Сложные адреса | Корпус/строение, дробь номера, буква, километраж, числовая улица, несколько домов | Сверить с преподавателем; ложный отказ оформить пересмотром с причиной, ложный зачёт блокирует выпуск |
| Тип и службы | Выбрать неверный конечный код в сгенерированном сценарии; пропустить требуемую службу; добавить лишнюю | Соответствующие критерии не выполнены. Условные СМП/МВД меняются при изменении признаков |
| Отправка фронта | Заполнить поля, выбрать код через дерево и отправить обычной кнопкой | Нет 422 из-за `tip_itog`; результат и разбор открываются |
| Зачёт/балл | Сделать критическую ошибку при высоком балле | Красный/незачтённый результат и в разборе, и в списке заданий; ручные 100 баллов не скрывают ошибку |
| Эталоны | В Network посмотреть `/api/scenarios`, `/api/assignments`, старт; до конца запросить разбор своей попытки | Нет `adres_etalon`, `kod_etalon`, скрытой `_pravda`; ранний разбор — 409. Запись исходного звонка в ДДС доступна намеренно |
| Чужая попытка | Под вторым обучающимся открыть разбор/завершение/аналитику первого | 403; данные не раскрыты |
| Двойное завершение | Повторить финальный HTTP-запрос через Network/инструмент клиента 4 раза | Один результат, одинаковые ответы; после перезапуска `app` повтор тоже возвращает сохранённый ответ |
| Версии | Начать попытку; преподавателем изменить/переопубликовать сценарий; закончить старую попытку | Старый разбор с прежним билетом/версией; новая попытка использует новый снимок |
| История | Изменить адрес дважды, поговорить, завершить и открыть «История действий» | Упорядоченные события, старое/новое поле; кнопка события в критерии открывает связанное событие |
| ДДС: только принять | Подтвердить приём и сразу завершить | Незачёт из-за отсутствия передачи и завершённого реагирования |
| ДДС: преждевременный статус | Установить «Работы завершены» до сведений бригады | Критическая ошибка статусов по факту |
| ДДС: полный цикл | Сверить запись, исправить ошибку, передать сведения, дождаться и принять звонки, проставить фактические статусы/комментарии | Ожидаемые критерии засчитываются; преподаватель отдельно проверяет смысл передачи, особенно отрицания и пострадавших |
| Непроверенная речь | Завершить без операторских реплик | Речь «не проверена», не зелёный успех; `bkt.n` речи не растёт |
| Пересмотр | Преподаватель пересматривает конкретный ошибочный критерий с причиной | Новая ревизия, исходная оценка сохранена, аналитика и BKT соответствующей программы пересчитаны; admin/trainee не могут пересматривать |
| Разделение программ | Пройти одну попытку 112 и одну ДДС; переключить «Мой прогресс» | Свои навыки и счётчики в каждом режиме; DDS не превращается в вызов с нормативом отправки 75 с |
| Холодный старт | Открыть прогресс нового обучающегося | «Не проверен», диагностический план; нет обещания «через 4 вызова готов» |
| Малые данные | 1–3 попытки | Видно n, широкий интервал; нет заявления о надёжном освоении |
| PDF/XLSX | Скачать оба режима, проверить кириллицу, длинный адрес, символы `< > &`, переносы | Факты/баллы совпадают с разбором; DDS показывает время подтверждения. Вёрстку проверяет человек |
| Старые данные | Развернуть копию существующей БД, открыть старые результаты | Записи на месте; архивная рубрика не подменена новой, нет выдуманной истории событий |
| Backup/restore | На стенде сохранить копию, сделать ещё попытку, восстановить копию | Состав попыток соответствует копии; новые таблицы включены; активная память перезагружена |

После перезапуска сервер восстанавливает `LIVE`, но полноценный пользовательский экран «возобновить занятие после перезагрузки браузера» этим патчем не добавляется. Проверка повторного завершения выполняется сохранённым HTTP-запросом.

## 4. Голос — обязательно руками с коллегой

1. В режиме 112 разрешить микрофон на HTTPS или localhost. Записать короткую фразу с адресом, длинную фразу, тишину; проверить текст ASR, отсутствие дубликата реплики, остановку микрофона.
2. Прослушать TTS-ответ; изменить голосовую настройку, которую внедряет коллега. Убедиться, что его версия работает после слияния.
3. Повторить в телефоне ДДС: исходящий звонок, голосовая реплика, ответ, входящий звонок, завершение.
4. На стенде отключить основной ASR предусмотренным коллегой способом, проверить его fallback и доступность текстового ввода. Вернуть сервис и повторить.
5. Два браузера одновременно: один ожидает медленный ответ LLM, второй заполняет карточку. Записать задержку сохранения, прогноза и финального запроса. Из-за глобальной сериализации она может быть заметной; если мешает сценарию хакатона, сначала исправить конкуренцию, не добавлять второй worker.

Не выдавать отсутствие изменений аудиофункций за доказательство качества звука. Автотест не оценит правильность распознавания дома/корпуса, естественность и задержку реального голоса.

## 5. ML-приёмка

- Флаг выключен: ответ прогноза содержит `ml_status=disabled`, эвристическая природа подписана.
- Флаг включён, файла нет/JSON повреждён/`approved=false`: HTTP 200, `ml_status=fallback_missing_invalid_or_unapproved`, приложение продолжает работать.
- Просрочить дедлайн с полностью заполненной карточкой: `veroyatnost=0`, независимо от артефакта.
- Обучить на слишком малом наборе: понятная ошибка; не выпускать фиктивную «обученную модель».
- На реальных данных изучить размеры train/calibration/test, число исключённых повторных обучающихся, Brier и baseline. Синтетический тест проверяет математику кода, не точность прогноза на заказчике.
- После ручного одобрения прошедшего проверку артефакта: `ml_status=active`, `method=logistic-calibrated-v1`, непустой SHA-256 `model_id`. Проверить, что после выключения флага возвращается эвристика.

Если автоматический тест не проходит, не заменять его ручным «вроде работает». Ручная проверка дополняет кодовые проверки для голоса, интерфейса, смысла сценариев и живой нагрузки; обнаруженную воспроизводимую ошибку сначала исправить.
