## 1. ТЗ Деп. обороны и ЧС

### 1.1. Заказчик и продукт

Заказчик по смыслу документа — **ГБУ «Система 112» Москвы**. Нужен тренажёр не для оператора, который принимает звонок на «112», а для **операторов ДДС**, которые работают с карточками на **АРМ-112**.

Целевая аудитория: специалисты ГБУ «Гормост», жилищные службы, прочие ДДС, преподаватели учебных центров, руководители диспетчерских служб.

Зачем: базовое обучение, переподготовка, аттестация, отработка нестандартных ситуаций, мониторинг учебного процесса. На рынке, по тексту ТЗ, нет ПО, которое учит работе с **реальным** интерфейсом системы-112.

Ключевые компоненты, которые ТЗ считает обязательными:

- эмуляция вызовов (IP-телефония / VoIP);
- модуль управления обучением и раздача заданий по сложности;
- оценка действий, в том числе нейросетевая;
- интерфейс преподавателя.

### 1.2. Границы

Сервис **не должен**:

- обрабатывать реальные экстренные вызовы;
- содержать боевой функционал системы-112 (только имитация);
- работать с конфиденциальными данными вне учебного процесса;
- выполнять функции реального диспетчерского центра.

Сервис **обязан**: изолированный локальный контур без внешнего интернета; защита учебных данных; масштабирование под группы; учёт действий; детальная отчётность; удалённый контроль занятия.

### 1.3. Обязательное ядро

- Эмуляция рабочих процессов в реальном времени.
- Входящие вызовы через виртуальную IP-телефонию **или** текстовые сообщения.
- LMS: распределение заданий, уровни сложности.
- Контроль тайминга и регламента, сравнение ручного ввода с **эталоном**.
- Оценка на базе ИИ, в том числе анализ текста карточки и грамматики.
- Многоуровневая аутентификация, RBAC, защита каналов, бэкап не реже 1 раза в сутки.
- Стыковка с форматами и **визуальными стандартами** ГБУ «Система 112».
- Локальное управление учётками и локальный мониторинг сервисов.

Норматив преподавателя по умолчанию: **30 секунд** на задание. Это не 75 с опроса оператора-112, а SLA ДДС на первичное «Принята / Не принята».

### 1.4. Опционально

Расширенная аналитика (графики, тепловые карты ошибок); экспорт Excel/PDF; пакетный импорт учебных материалов; адаптивный веб для мобильных в локальной сети; внутренний API без внешних интеграций.

### 1.5. Производительность

В локальной сети: отклик UI ≤ 2 с при нагрузке до 100 пользователей; ≥ 20 одновременных сессий (вызовов/карточек); задержка VoIP ≤ 150 мс; восстановление сессий после сбоя сети до 30 с без потери данных. Запись в БД ≥ 100 операций/с; аналитический отчёт ≤ 30 с. Вертикальное и горизонтальное масштабирование.

Рабочее место обучающегося: Intel Core i5 (или аналог), от 16 ГБ ОЗУ, SSD от 256 ГБ, Gigabit Ethernet, гарнитура VoIP, IP-телефон. Сервер ИИ-модуля: 6+ ядер, от 32 ГБ ОЗУ, NVMe от 512 ГБ.

### 1.6. Роли

**Администратор.** Старт/стоп сервисов, мониторинг, бэкап, пакетные обновления, CRUD учёток и ролей, блокировка, SIP/БД/безопасность/логи, аудит. Не может менять оценки и сценарии во время активного занятия; не удаляет критичные данные без бэкапа; принцип минимальных привилегий к ПДн.

**Преподаватель.** CRUD и валидация сценариев (в том числе сгенерированных нейросетью); назначение заданий группам; живой контроль; прогресс; материалы; сложность; автооценка ИИ + экспертная оценка; отчёты; инсайты по ошибкам группы; комментарии обучающимся; параметры сценария (тип, локация, сложность); тайминг (по умолчанию 30 с); пороги ошибок и синтаксиса. Не трогает админ-настройки, чужие занятия, оценки без записи в журнал аудита.

**Обучающийся.** Только назначенные материалы; эмуляция АРМ-112; приём вызовов/сообщений; заполнение карточки; свои оценки, таймер, история ошибок, рекомендации ИИ. Нет доступа к админке, чужим результатам, правке сценариев и удалению своей истории. Вход с аутентификацией каждый раз.

Интерфейс: русский язык, единая стилистика, адаптивность, десктоп и мобильная/планшетная вёрстка.

### 1.7. Учебные сценарии ТЗ

**Настройка среды.** Вход в локальный комплекс → преподаватель выбирает категории событий → нейросеть генерирует типы (ДТП, пожары, медицина и др.) → система строит эталон → преподаватель утверждает частично или полностью → ролевая модель так, чтобы в ленту попадали только **профильные** события (Мосводоканал, Москоллектор, управы, газ и т.п.) → предпросмотр с подсветкой правильных действий → контекстная коррекция эталона → загрузка материалов → проверка грамматики.

**Занятие «карточки».** Преподаватель стартует занятие → система имитирует звонок → обучающийся заполняет карточку в эмуляции АРМ-112 → преподаватель завершает → отчёт: действия, ошибки, время заполнения, отклонение от норматива, грамматика.

**Занятие «действия с карточками».** Преподаватель выбирает источник карточек: сгенерированные системой / сформированные обучающимися / смесь → случайная карточка → обучающийся **действует** (в том числе вводит текст вроде «Сообщение принято, дежурная бригада направлена на место») → следующая карточка → отчёт того же состава. Это и есть основной поток ДДС, а не опрос заявителя.

### 1.8. Данные, сдача, экспертиза

Форматы: JSON (сценарии, API, профили), XML (конфиги, legacy), CSV (отчёты), SQL/PostgreSQL ≥ 12, PDF (сертификаты, документы), MP3/WAV (учебные вызовы), DOCX (методички).

Сдача: ссылка на репозиторий с открытым не обфусцированным кодом; презентация pptx/pdf; прототип; сопроводительная документация (методы, ограничения, сборка, архитектура). Правовая рамка: 149-ФЗ, 152-ФЗ.

НФТ: бэкап ежедневно; отказоустойчивость в локальном кластере; автовосстановление; аудит действий; TLS внутри контура; хранение журналов безопасности ≥ 6 месяцев; ОС Windows 10/11 и Ubuntu 20.04+; Chrome / Firefox / Яндекс.Браузер; SIP-сервер в контуре.

## 2. Памятка АРМ-112 (ОКр, 2025)

Документ **не** учебник и не инструкция по эксплуатации. Это систематизация вопросов ДДС. Терминов **УКИО**, **УЧОЛ**, **ЕДДС** в нём нет. Рабочая сущность — **карточка происшествия (КП)** в **ПОВ-112**.

### 2.1. Кто есть кто

Принцип «одного окна»: заявитель один раз звонит на «112» и говорит с одним оператором. Оператор классифицирует, регистрирует, направляет службам. Службы до конца работ пишут ход реагирования в ту же систему. Контроль — **Отдел контроля реагирования (ОКр)**.

| Роль | Делает |
|---|---|
| ГБУ «Система 112» | Оператор системы-112 Москвы |
| Специалист-112 | Принимает «112», заполняет и сохраняет КП |
| Главный специалист-112 | Ставит статус карточки «Проверена» |
| Диспетчер ДДС | Работает на АРМ-112 со **своим** блоком оповещения |
| ОКр | Мониторинг, звонки при нарушениях, методика |
| СТП | Техподдержка ПОВ-112 (не подразделение ГБУ) |
| ВИС | Внешние ИС служб (101/102/103/104, ЦОДД, Мосводоканал, ЭРА-ГЛОНАСС, 112 МО/КО) |

Способы подключения службы: интеграция ИС; удалённый АРМ-112; только телефон; служба-посредник; комбинация.

Источники карточек: звонки и СМС в Службу 112 **и** автоматический приход из ВИС. Особенность Москвы: КП создают не только операторы «112».

Норматив для служб (из ПП РФ 1931, повторено в памятке): диспетчер **подтверждает получение за 30 секунд**.

На февраль 2025 в Москве **> 210** участников информационного взаимодействия.

### 2.2. Как устроена карточка

Блоки КП:

1. Адрес (зарегистрированный + описательный; иконка карты; адрес может не совпадать с фактическим местом).
2. Формализованные признаки происшествия (выбор оператора-112).
3. Опросная карта (неформализованные ответы).
4. Описание — читать целиком.
5. **Итоговый тип** — из комбинации признаков.
6. **Список оповещения** — почти всегда автоматически по **ЕКП**. Оператор-112 может **добавить** службу, **удалить не может**. Часть служб (аналитические) в списке скрыта.
7. Блоки оповещения по каждой службе: статусы реагирования и комментарии; у ВИС автор «оп. 9999», у АРМ-112 — ФИО или номер.

Карточки из ВИС беднее: часто нет номера РМ оператора, не всегда опросная карта, нет формализованных признаков.

Соответствие типов между системами **не дословное**. Пример: «Пожар: подъезд» в S112 ↔ «Пожар» в ИС 102; «Пожар» в 102 → «Пожар: прочие объекты» в S112.

### 2.3. Статусы карточки

| Статус | Смысл |
|---|---|
| Зарегистрирована | КП сохранена |
| Отработана | Оповещение служб завершено (только карточки Службы 112) |
| Проверена | Главный специалист-112 проверил работу оператора |
| Не оповещено | > 30 с нет «Принята» / «Не принята» |
| Отказ | Служба отказалась, карточка проверена |
| Не завершено | > 48 ч с сохранения, есть служба без «Работы завершены» |
| Завершена | Все службы закрыли работы **или** список оповещения пуст |

«Не оповещено», «Отказ», «Не завершено» — красная ячейка и спецраздел ОКр.

### 2.4. Статусы реагирования ДДС

Технические: **Добавлена** (при сохранении КП), **Получена службой** (интеграция дошла / диспетчер открыл карточку на АРМ-112).

Первичные, обязательны за **30 с**:

- **Принята** — реагирование будет;
- **Не принята** — реагирования не будет; **обязателен комментарий** (причина, кому передано). Потом можно сменить на «Принята».

После «Принята», только последовательно, кнопка «карандаш» в блоке **своей** службы:

Начало реагирования → Прибытие → Проведение работ → **Работы завершены** (закрывает редактирование) **или** **Отказ от выполнения работ** (тоже закрывает; комментарий обязателен).

Особенности: служба 103 не ставит «Не принята» / «Отказ от выполнения работ», вместо них «Работы завершены: Завершение работ без бригады». Служба 104 не всегда пишет комментарии (интеграция).

Правила: статус = факт; нельзя отказываться только потому, что реагирует другая служба; комментарии обязательны при отказах.

Если ситуация изменилась и нужны другие службы — **звонить на 112**, представиться, назвать адрес и номер КП.

Ошибочно «Работы завершены» / недоступен комментарий / неправомерный отказ другой службы — звонок в ОКр: 8 (495) 694-71-89. По старым суткам — официальный запрос, не звонок.

### 2.5. Чему учить по памятке

1. Различать оператора-112, диспетчера ДДС, ВИС и ОКр.
2. Читать КП от 112 и КП из ВИС по-разному.
3. Укладываться в 30 с на «Принята / Не принята».
4. Комментировать отказы и передачи.
5. Не путать «Не принята», «Отказ от выполнения работ» и «Работы завершены».
6. Вести ход работ при длительных заявках.
7. Не отказывать в профиле без обоснования.
8. Знать эскалацию: СТП (техника), ОКр (оперативка), МосЭДО (учётки).

Типовые ошибки, которые ловит ОКр: нет статуса; «Принята» при том, что работ не будет; отказ от профильного; пустой или неполный комментарий; нет статусов хода работ; нет связи с местом АРМ.

### 2.6. UI ПОВ-112, который должен узнавать обучаемый

Вход «Войти», контакты СТП, «?» → «Сообщить о проблеме», бегунок автообновления вправо, поиск и расширенный поиск, лента поступивших КП, вкладки по роли, красные проблемные статусы, адрес + карта, признаки, опросная карта, блоки служб, «карандаш», комментарии.

Поиск только среди карточек, **полученных этой службой**. Признаки 3-го уровня и глубже поиском не находятся.
